# Plan: v0.1 M1 Format

**Status:** Draft
**Base:** `origin/main @ 462191d`
**Tracking issue:** —

## Goal

Finish milestone M1 of the v0.1 plan (`specs/001-agent-log-tracer/plan.md` section 4, tasks 2 to 10). When it is done, eagain has its settings system, a pinned OTLP trace reader and writer, `eagain validate`, the internal model and normaliser, synthetic and real OTLP fixtures, and the corpus test tier that every later pull request must pass. This covers Spec 001 FR-1 and FR-2 and the v0.1 parts of Spec 003 FR-19 and FR-20. M2 to M6 build on all of it.

## Context

- Task 1 of M1, the project scaffold, merged with PR #1. It includes the uv project, a stub `eagain --version`, CLI exit codes (FR-7 AC2), network blocked in tests, and CI on Python 3.11 and 3.14.
- Specs are approved and are the source of truth. Requirement numbers are cited, not copied. Sources read: Spec 001 sections 4 to 6 and 8 to 9; Spec 003 sections 2 to 4 and 7; plan sections 1 to 5 and 7; `CLAUDE.md`.
- Constraints that apply throughout:
  - The core has no runtime dependencies (plan section 1). OTLP JSON is read and written by hand, and TOML is parsed with `tomllib`.
  - Rules, metrics and report read only the internal model. `normalise.py` is the only reader of `gen_ai.*` names (plan section 2).
  - Fixtures are synthetic. Corpus and live data are never committed, quoted or printed, and tests on them assert counts only (plan section 5).
  - No network, except the corpus download step, which runs before tests start.
  - Every acceptance criterion a task touches gets a test named `test_frN_acM_...`. `.wf.toml` enforces this.

## Approach

The work runs in three tracks that can proceed in parallel. They join at the M1 sign-off.

1. **Settings** (Spec 003). One typed settings definition holds each setting's name, type, default, validation and whether project config may set it. Loading, origin tracking, `config show`, `config validate`, `config init` and the generated docs all read from it (FR-19 AC9). M1 defines the mechanism and the settings already fixed by Spec 003 for v0.1: paths, reports, redaction, LLM, operation, and explicit project ID. Each rule's thresholds are added with that rule in M2.
2. **Trace format** (Spec 001 section 5).
   - `semconv.py` pins the conventions versions and names every attribute.
   - `otlp/` reads and writes OTLP JSON Lines.
   - `normalise.py` builds `model.py` objects. It resolves outcomes and error text using the orders given in section 5, and sorts spans by start time, then span ID.
   - `eagain validate` sits on the reader.
   - Fixtures prove both directions: a generated one for a fictional agent, and one captured once from real OpenTelemetry tooling.
3. **Test gate** (plan section 5).
   - A hash-checked corpus registry and fetcher, using the standard library only.
   - An independent oracle script with its committed expected counts.
   - Count-only assertion helpers.
   - A CI job for the corpus tier.
   - A spec coverage report built from test names.

FR-2 AC1 needs the M2 rules (`tool-failure`, `repeated-error`, `recurring-failure`). M1 delivers the fictional-agent fixture, and the AC1 test lands in M2 with those rules.

## Out of scope

- Rules, metrics, redaction and reports (M2 onwards). FR-21's redaction limits arrive with redaction in M2.
- The settings hash in reports (FR-19 AC7, M2 task 5), and listing uncaptured data in coverage (FR-19 AC8, M2 and M4).
- Stating in reports that a project config was applied (FR-20 AC5, M4).
- The Claude Code importer (M3). Corpus checks that need it (accounting, oracle agreement with eagain) start in M3.

## Risks and open questions

- **Collector availability (plan open item 2).** T9 needs an OpenTelemetry Collector once. Docker is installed locally, so T9 uses the `otel/opentelemetry-collector-contrib` image. The captured file is committed, so CI never needs the Collector.
- **Conventions drift.** The GenAI conventions are at Development stability. T4 pins `semantic-conventions-genai` at commit `9d1e748` and `semantic-conventions` at v1.45.0. Moving to newer versions means re-checking the mapping.
- **M1 live run.** The importer arrives in M3, so the M1 live tier runs the oracle script on `~/.claude/projects` (aggregates only). This also checks that the oracle handles the newer local transcript format (plan section 6). Decided with the owner.
- **Branch protection (T14)** changes repository settings. It is an owner task and is never labelled `status:ready`.

## Tasks

### T1: Settings definition and loader

Plan M1.2, part 1. Create `src/eagain/config/` with one typed settings definition for the v0.1 settings in Spec 003 section 3 (paths, reports, redaction, LLM, operation, explicit project ID, `preset`). Each setting records its name, type, default, validation, when it applies, and whether project config may set it. A loader merges the sources in Spec 003 section 2 in order: defaults, preset, user config (`EAGAIN_HOME` or `~/.config/eagain/config.toml`), project `.eagain.toml`, `EAGAIN_<SECTION>_<KEY>` environment variables, then flags. It records the origin of each value. Files carry a version field. Unknown keys warn and name the closest valid key. The loader uses `tomllib` only. This task covers no CLI commands.

**Depends on:** —

**Acceptance criteria:**
- FR-19 AC1
- FR-19 AC4
- FR-19 AC6
- The precedence order of Spec 003 section 2 holds, with a test that sets one key in every source.

### T2: Project config limits

Plan M1.2, part 2. Make the loader enforce Spec 003 FR-20 on `.eagain.toml`, which is untrusted.
- Allow only the settings the definition marks as project-settable.
- Let project config tighten capture and retention limits, never loosen them.
- Accept redaction patterns from project config only as literal strings.
- Ignore LLM, path, sharing, group, allowlist and draft-location keys, with a warning.
- Honour `--no-project-config`.

**Depends on:** T1

**Acceptance criteria:**
- FR-20 AC1

### T5: OTLP JSON Lines reader and writer

Plan M1.4. Create `src/eagain/otlp/` with a hand-written reader and writer for the OTLP File format (one `resourceSpans` object per line). It handles every attribute value type (string, bool, int, double, array, kvlist, bytes), integer-as-string timestamps, and hex trace and span IDs. Errors report the line number and the reason. Logs and metrics files are detected and reported as such. Writing is deterministic: the same spans always give the same bytes.

**Depends on:** T4

**Acceptance criteria:**
- A Hypothesis property test shows that write then read round-trips any span, including every attribute value type.
- Malformed lines give errors carrying the line number and reason. One bad line does not stop the remaining lines being read.
- Writing the same spans twice gives byte-identical output.

### T6: eagain validate

Plan M1.5. Add `eagain validate <file>` on top of the reader. It checks OTLP structure and the GenAI expectations in Spec 001 section 5, and prints trace, span and `execute_tool` counts. Missing parents and spans with no `gen_ai.operation.name` give warnings, not errors. Logs and metrics files are rejected.

**Depends on:** T5

**Acceptance criteria:**
- FR-1 AC1
- FR-1 AC2
- FR-1 AC3
- FR-1 AC4

### T7: Internal model and normaliser

Plan M1.6.
- Create `src/eagain/model.py` with `Session`, `Step`, `ToolCall`, `ModelCall` and `Outcome`.
- Create `src/eagain/normalise.py`, which turns OTLP spans into the model:
  - assemble spans by `traceId` and `parentSpanId`, sort them by start time then span ID, and treat child `invoke_agent` spans as subagent runs;
  - resolve outcomes in the order of section 5 ("Determining a tool's outcome") and error text in the order of section 5 ("Error text for fingerprints");
  - ignore and count non-GenAI spans for coverage.
- `normalise.py` is the only module that reads `gen_ai.*` names.
- Add the plan section 2 test that `rules`, `metrics` and `report` import `model`, never `otlp`, `semconv` or `importers`.

**Depends on:** T4, T5

**Acceptance criteria:**
- FR-2 AC3
- The outcome order holds: an explicit `eagain.tool.outcome` wins; then `ERROR` status or `error.type` gives `error`; otherwise the outcome is `ok`. A test covers each branch.
- Shuffling input lines gives an identical model.
- The dependency-direction test exists and passes.

### T8: Synthetic fixture generator and fictional-agent fixture

**Depends on:** T7

**Acceptance criteria:**

- The fixture uses no `eagain.*` attributes, and a test asserts this.

### T10: Corpus registry, fetcher and CI corpus job

Plan M1.9, part 1. Add `tests/corpora/registry.toml` with the four corpora in plan section 5: dataset, revision, license and a SHA-256 for every file. Add a fetcher that uses the standard library only, downloads into `.corpora/` (gitignored), checks every hash, and caches downloads.
- In CI, a download failure fails the run.
- Locally, the corpus tier is skipped with a clear message unless `EAGAIN_REQUIRE_CORPORA=1`.

Add count-only assertion helpers that never print compared values. Add the `corpus` CI job, which downloads with caching before tests start. Adding `registry.toml` makes the corpus check in `.wf.toml` mandatory, so the task must ship at least one corpus test, for example registry integrity plus file and line counts.

**Depends on:** —

**Acceptance criteria:**
- A hash mismatch fails the run, and the failure message names the file but no content.
- With `EAGAIN_REQUIRE_CORPORA=1` and no data, the tier fails rather than skips.
- The count helpers' failure messages contain counts and IDs only, and a test asserts this.
- The corpus CI job passes on the pull request.

### T11: Oracle script and expected counts

Add corpus tests that rerun the oracle and compare its counts with the expected files.

**Depends on:** T10

**Acceptance criteria:**

- The oracle imports nothing from `eagain`, and a test checks this.
- The hand-check method and its sample size are recorded in the work plan's Outcome, as aggregates only.
